# Security Features

Everything on this page works out of the box. This page explains what each feature does, where it lives and what to configure.

## Two-factor authentication

TOTP (authenticator app) with backup codes, using Better-Auth's `twoFactor` plugin.

- **Users enable it** under Dashboard → Settings → Security: password confirm, QR code, verify a code, save backup codes. Backup codes can be regenerated there.
- **At sign-in**, once email/password succeeds, the user is sent to `/login/2fa` to enter a TOTP or backup code.
- The authenticator app shows `APP_NAME` as the issuer.
- Data: the `twoFactor` table plus `user.twoFactorEnabled`.

## Passkeys

WebAuthn sign-in (Touch ID, Windows Hello, security keys), using `@better-auth/passkey`.

- Users register and remove passkeys under Settings → Security. Sign in with the **Sign in with a passkey** button on `/login`.
- Each add or remove emails the user (if Resend is configured) and writes `passkey_added` or `passkey_removed` to the activity log.
- The relying-party ID is derived from `BETTER_AUTH_URL`.

<Callout type="warning">
Passkeys are bound to the hostname in `BETTER_AUTH_URL`. Passkeys registered on `localhost` won't work in production, and moving domains invalidates every passkey.
</Callout>

## Active sessions

Dashboard → **Active sessions** lists each session with its device, IP and approximate location. Users can revoke any of them except the current one, via `POST /api/sessions/revoke`.

An admin can turn revocation off globally in System Settings, and the endpoint then returns `403`. Admins can also revoke any user's sessions from the user detail page.

## New-device alerts

1. After sign-in, `<DeviceCheck />` (mounted in the root layout) computes a FingerprintJS visitor ID and posts it to `/api/device-check`, once per browser session.
2. If this (user, device) pair has never been seen, the server records it in `device_fingerprint`. It then emails **the user and every admin** and lists the device on the admin **New devices** card.

The check only runs after the visitor allows the security fingerprint (when consent is required). Emails are skipped without `RESEND_API_KEY`, but the device is still recorded.

## Sign-in throttle

`/sign-in/email` and `/sign-up/email` are rate-limited per device, in `hooks.before` in `server/auth.ts`:

| Key | Limit | Window |
|---|---|---|
| FingerprintJS visitor ID (`x-device-fingerprint` header) | 10 | 15 min |
| Client IP (backstop, for when the header is missing or spoofed) | 30 | 15 min |

- **Sign-in:** failures count toward the limit, and a successful sign-in resets it.
- **Sign-up:** every attempt counts, because mass sign-ups are the abuse being limited.
- Over the limit, the endpoint returns `429` with "Too many attempts from this device".
- **Retention:** each row stores the last IP, user agent and email typed, often for people without an account. Rows untouched for 30 days are deleted. The sweep runs on the sign-in path, at most hourly per server instance, so no cron is needed. On a site with no sign-in attempts, old rows stay until the next attempt; if you need a hard guarantee, call `pruneStaleRows()` from `lib/auth-throttle.ts` on a schedule.

The limits (`WINDOW_MS`, `MAX`, `RETENTION_MS`) are fixed inside the package's auth. Editing your local `lib/auth-throttle-limits.ts` has no effect unless you also use your own `server/auth.ts` (see [Customizing package code](/architecture#customizing-package-code)). Throttled devices appear on the admin **Device throttle** card.

<Callout type="info">
The client IP comes from `x-forwarded-for` (first entry), falling back to `x-real-ip`. Behind your own reverse proxy, make sure it sets one of these. Otherwise every request shares one IP, and the IP cap throttles everyone at once.
</Callout>

## Shared-device detection

The admin **Shared devices** card lists any fingerprint used by 3 or more accounts, a common sign of multi-accounting or trial abuse. Each account links to its detail page, where you can ban it.

## Account deletion

Dashboard → Settings → **Danger zone** lets users delete their own account, using Better-Auth's `deleteUser`.

- Credential users confirm with their password. OAuth-only users need a session less than 24 hours old, otherwise they're asked to sign in again.
- It's blocked while an admin is impersonating the user, and for the last remaining admin.
- All of the user's rows cascade-delete.

## Cookie consent

`<CookieBanner />` (root layout) offers **Necessary only**, **Customize** and **Accept all**, and stores the choice in the `cookie_consent` cookie for one year. **Cookie settings** in the footer reopens it.

Consent is given **per purpose**, as regulators such as the CNIL expect, because the two optional features serve unrelated ends:

| Purpose (`ConsentPurpose`) | What it allows | Without it |
|---|---|---|
| `fingerprint` | FingerprintJS device ID: new-device alerts, throttle, shared-device detection, admin Devices card | New-device alerts are skipped; the throttle uses its IP cap |
| `onetap` | Google One Tap, whose script may set Google's cookies | The One Tap prompt doesn't appear |

**Customize** shows one unticked checkbox per purpose; pre-ticked boxes aren't valid consent. The cookie holds `all`, `necessary` or a comma list of the ticked purposes (for example `fingerprint`).

### Consent mode

**Require consent (GDPR / ePrivacy)** in System Settings decides whether any of this applies:

- **On:** the banner shows, and fingerprinting and One Tap each wait for consent to their purpose. `/api/device-check` also checks the `cookie_consent` cookie itself and returns `403` unless it allows `fingerprint` (`consentAllows()` in `lib/cookie-names.ts`), so a stale or modified client can't record a device without consent.
- **Off:** no banner and no "Cookie settings" link. Everything runs for every visitor as if they had accepted.

<Callout type="error">
**Turning consent off is illegal for EU and UK visitors.** Turning off **Require consent**, or setting `NEXT_PUBLIC_COOKIE_BANNER=false`, means every visitor is fingerprinted and shown Google One Tap without being asked. Under the ePrivacy Directive (Art. 5(3)) and GDPR, that breaks the law for anyone in the EU, the EEA or the UK, whatever your legitimate-interest reasoning. Regulators have confirmed that fingerprinting counts as storing or reading information on the device (EDPB Guidelines 2/2023). Turn it off only if none of your users are in those regions or in any other region with similar consent rules. If you're not sure, leave it on.
</Callout>

Until an admin saves the setting, it follows `NEXT_PUBLIC_COOKIE_BANNER`, so migrating never flips a deployed banner. `proxy.ts` copies the effective value into a `consent_required` cookie (`1`/`0`) that `lib/cookie-consent.ts` reads, so the root layout stays static. Changes reach every instance within the 10-second settings cache.

The placeholder `/privacy` page follows the setting too. It's rendered per request and describes the consent flow when consent is on, or says fingerprinting runs for every visitor when it's off. It also covers the legal basis, retention, third parties (Resend, Google) and user rights. `/terms` has a short security and abuse-prevention clause that links to it. Both are templates: rewrite them for your deployment.

**Withdrawing fingerprint consent erases the device record.** While it's given, the device ID is also kept in `localStorage` (`device-visitor-id`). When the visitor's choice stops including `fingerprint` (**Necessary only**, or unticked under **Customize**), `<DeviceCheck />` sends it to `DELETE /api/device-check`. That deletes the signed-in user's `device_fingerprint` row for this device, then forgets the ID. If they withdraw while signed out, the erasure happens at their next sign-in. If they consent again later, the device is recorded as new, which sends a new-device email.

Not erased: other accounts' rows for the same browser, which stay until those accounts are deleted, so one person's choice can't erase other accounts' security records; and `auth_throttle` rows. Throttle rows are security data kept for 30 days. Erasing them on request would let an attacker reset their own throttle.

<Callout type="warning">
Projects scaffolded before this change have a local `app/api/device-check/route.ts` without the `DELETE` handler. Bumping the package updates `<DeviceCheck />` but not the route, so copy the `DELETE` export from the template's route. Until you do, the request gets a 405, the ID stays stored and the erasure is retried on each page load.
</Callout>

Withdrawing One Tap consent stops its script from loading and deletes Google's `g_state` cookie.

Gate your own analytics the same way:

```tsx
import { useCookieConsent, useConsentFor } from "@/lib/cookie-consent"

const consent = useCookieConsent() // "all" | "necessary" | "custom" | null
if (consent === "all") loadAnalytics()

const fingerprintAllowed = useConsentFor("fingerprint") // per purpose
```

To give your own feature a separate choice, add a purpose to `ConsentPurpose` / `CONSENT_PURPOSES` in `lib/cookie-names.ts` and to `PURPOSES` in the banner. Both ship in the package, so that needs your own copies (see [Customizing package code](/architecture#customizing-package-code)).

If none of your users are in the EU, the UK or another consent-rules region, you can drop the banner: turn **Require consent** off in System Settings, or set `NEXT_PUBLIC_COOKIE_BANNER=false` to make that the default. Consent is then treated as granted for everyone. For an EU or UK audience that's a violation; see the warning under [Consent mode](#consent-mode).

<Callout type="warning">
Upgrading from an earlier version: run `bun run generate` and migrate. That adds `system_settings."consentRequired"` and `device_fingerprint.components`. Until you migrate, settings reads fail open to env defaults. Three files are local to your project and don't update with the package: `proxy.ts` (sets the `consent_required` cookie; without it the client falls back to `NEXT_PUBLIC_COOKIE_BANNER`), `app/api/device-check/route.ts` (the consent check and signal storage; an older route that checks `cookie_consent === "all"` refuses visitors who allowed only `fingerprint` under **Customize**) and `app/dashboard/admin/users/[userId]/page.tsx` (renders `<AdminUserDevicesCard />`). Copy the changes from the template.
</Callout>

## Open-redirect protection

Every `callbackUrl` goes through `normalizeCallbackUrl()`, which drops anything off-origin. Use it for any redirect target you accept from a query string.
